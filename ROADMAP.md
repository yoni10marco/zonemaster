# Zone Master roadmap

## Next: training with friends

Add friends and plan training together. **Status: all three slices built, tested and pushed.**

### Progress

- **Slice 1: identity and friends. Built.**
  - Database (already applied to the live database, migrations 0009 and 0010): username, immutable friend ID, `friendships`, and the friend functions with rate limits.
  - App: the friend ID card in Settings, the Friends page (find, requests, list, unfriend, block) and the menu badge.

  - Known and expected: the Supabase advisor lists the friend functions as "signed-in users can execute a SECURITY DEFINER function". That is the intended API; each function checks the caller and returns only a username and the state of the relationship.
- **Slice 2: shared sessions. Built and pushed** (migrations 0011 and 0012 applied to the live database; real-browser walkthrough done; the invite card hides the inviter from the "With" list).

- **Follow-ups (built):** optional username field at signup (migration 0015), the coach knows which sessions are shared and with whom (only accepted friends' usernames and whether they finished), and a "Delete account" button in Settings (migration 0016, `delete_my_account()`, typed confirmation).

### Decisions (from the product owner)

1. **Finding friends:** every profile gets a **username** and a **friend ID**. The friend ID is created at signup and can never be changed. To add someone you must know **both** their username and their friend ID (like `alex` + `K7M2-9QXA`). There is no search-by-email and no browsing of users.
2. **Privacy:** being friends shows a friend **nothing** of your calendar. A friend only ever sees:
   - sessions you **planned together** (a session you both belong to), and
   - whether you **completed those together**.
   Your personal planned and completed workouts, profile, race goal, heart rate and coach chat stay private, always. There are no per-friend visibility settings to manage, because sharing happens per session.
3. **Notifications:** an in-app badge only (pending friend requests and session invites). No email, no push.
4. **Shared sessions (confirmed):** one shared record says what was planned together; each person gets **their own independent copy** on their calendar, linked to it. Moving or editing your own copy never affects the friend's. Deleting your copy means leaving the session.
5. **Username (confirmed):** can be changed later; it need not be unique, because the friend ID identifies the person.

### How it works for a user

- **Settings:** a new "Friends" card shows your username (editable) and your friend ID (read-only, with a Copy button). Until a username is set you cannot be found. Existing accounts get a friend ID automatically and are asked to choose a username.
- **Friends page** (new menu item with a badge): tabs for *Friends*, *Requests* and *Add friend*.
  - *Add friend:* enter username + friend ID, see the match, send a request.
  - *Requests:* accept or decline incoming friend requests and session invites; cancel requests you sent.
  - *Friends:* your friends, with Unfriend and Block.
- **Planning together:** in the workout form, a "Do it together" section lets you pick friends. They get an invite; when they accept, the session is added to their calendar as their own copy. Cards show "With Alex" and each person's done-state (waiting / done).
- **Completing together:** each person ticks their own copy as done. Everyone in the session can see who has completed it, nothing more (no durations, distances or notes). When two or more have completed it, it shows as *Done together*.
- **Dashboard:** a small "Trained together" count for the period.

### Data model (new migration, all additive)

| Table / change | Purpose |
|---|---|
| `profiles` + `username`, `friend_code` | `friend_code` is unique, generated by the database at signup (8 characters, no look-alikes), and protected by a trigger so it can never be updated. |
| `friendships` | requester, addressee, status (`pending` / `accepted` / `blocked`); one row per pair, never duplicated in either direction; cannot befriend yourself. |
| `shared_sessions` | the planned-together record: creator, date, discipline, title, notes, target duration/distance/zone. |
| `shared_session_members` | who is in a session: status (`invited` / `accepted` / `declined`) and a link to that member's own calendar copy. |
| `planned_workouts` + `shared_session_id` | lets a calendar card show "With Alex". Existing owner-only rules stay exactly as they are. |

### Security rules (the important part)

- No policy ever lets one user read another user's `planned_workouts`, `completed_workouts`, `profiles` or `ai_chat_history`. Everything a friend may see comes through a few `security definer` functions that return only: username, friendship state, session details, and a per-member "completed yes/no".
- The functions pin their `search_path`, and execution is granted to logged-in users only.
- Finding a user requires the exact username **and** friend ID; lookups are rate-limited per user, so IDs cannot be guessed (32^8 possibilities plus the throttle).
- Friend requests are rate-limited; Block hides you from that person entirely.
- **Unfriend / block** removes both of you from each other's shared sessions; the calendar copies stay as ordinary workouts and the link is cleared.
- Deleting an account deletes its friendships and memberships.
- After the migration: run the Supabase security and performance advisors, and test the policies directly in SQL as two different users (a rolled-back transaction) to prove a friend cannot read anything personal.

### Delivery in three slices (each one tested, then pushed)

**Slice 1 — Identity and friends (medium).** Migration for username / friend ID / friendships, the friend functions, the Settings card, the Friends page (add, requests, list, unfriend, block) and the badge.

**Slice 2 — Shared sessions (large).** `shared_sessions` and members, invite / accept / decline / leave, the "Do it together" section in the workout form, "With Alex" cards, completion status.

**Slice 3 — Polish (small).** "Trained together" on the dashboard, rate limits and empty states, cleanup on unfriend, undo where it makes sense.

### Testing plan

- **Database:** SQL tests as two users proving each rule above (cannot read the other's workouts, can read only shared sessions, can't edit the friend ID, can't duplicate friendships, throttles work).
- **Logic and UI:** Vitest for validation (username rules, friend ID format), the friends and invites components (with a mocked backend), and the new form section.
- **In the real app:** the same approach as before — baseline the database, exercise each flow, delete the test data, and confirm the counts match.
- The existing `npm run check` and the GitHub workflow keep guarding everything.

### Settled details

- Username rules: 3–20 characters, lowercase letters, numbers and underscore.
- A shared session holds at most 8 people.

## Small fixes and polish (2026-10-01)

- **Mobile bottom navigation.** A fixed tab bar across the bottom of the screen on phones (Calendar, Dashboard, Coach, Friends, Profile), replacing the old icon-only top nav on small screens. The top nav's own links now only show at the `sm` breakpoint and up, so there is exactly one nav at a time (`BottomNav.tsx`).
- **Double-submit fix.** Adding, saving or deleting a workout is now guarded against a second tap landing before the first save finishes (a disabled button with a spinner while saving) — the bug where tapping Save twice by mistake created the workout twice.
- **Multi-sport ("brick") workouts.** One calendar entry can now cover more than one discipline (e.g. a bike leg then a run leg), added from the workout form's "Add another sport" section. It is still one session everywhere a session is counted (dashboard completion rate, "Trained together"), but the dashboard's per-discipline activity counts add one for *each* discipline it covers. Migration 0017 adds a validated `extra_segments` JSON column to `planned_workouts` and `completed_workouts` (leg 1 stays in the existing columns, unchanged for every ordinary workout); `src/lib/utils/segments.ts` is the one place that turns a row into "its legs" and back. Copy/repeat/duplicate carry every leg along. The coach sees brick workouts as one session with a "Bike, 60 min + Run, 20 min" style line. Import matching deliberately never links a single activity file to a multi-sport workout (one file can't say which leg it is), so a brick is always ticked off by hand.

## Login-wait animation and general snappiness (2026-10-01)

Scope was deliberately "visible polish", not a deep performance rework (declined by the owner).

- ~~Branded loading screens~~ **Built, then removed the next day — see below: it turned out to hang the app.** The fade between pages and the spinner fixes below stayed; they don't depend on it.
- **A quick fade between pages.** Switching between Calendar/Dashboard/Coach/Friends/Settings (and between Login/Signup) gets a short fade-in instead of an abrupt pop, while the nav/chrome around it stays put (`PageTransition.tsx`, reusing the same `animate-in fade-in-0` the dialogs already use). - **Spinner consistency sweep.** Every button that does something that takes a moment (save profile, confirm a destructive action, accept/decline a session invite, send a shared-session invitation) now shows the same spinner the rest of the app already used in a few places, instead of plain disabled text in some and nothing in others.

## Coach brick suggestions, zone "None", a more colorful workout form (2026-10-02)

- **Found and fixed a serious regression from the entry above.** The `loading.tsx` files added for "branded loading screens" hung the app completely in this Next.js version: any navigation into `(app)/*` showed the loading spinner forever and never rendered the real page, even though the server had already returned the correct content (confirmed via a direct `fetch()` and the server's own request log — purely a client-side Suspense/streaming issue; reproduced on a freshly restarted dev server and a brand-new tab, then isolated by removing each `loading.tsx` one at a time). The cause narrows to a `loading.tsx` existing anywhere alongside `(app)/layout.tsx`'s async, conditionally-redirecting auth check. Fix: removed all three `loading.tsx` files (root, `(app)`, `(auth)`) and the now-unused `PageLoading` component; kept `PageTransition` (confirmed safe on its own) and the spinner-consistency work. The app no longer has an instant loading skeleton on navigation, only the page-switch fade and each page's own existing loading state (e.g. the calendar's own skeleton, which fetches client-side and was never part of this bug).
- **Zone "None" fix.** Once you picked a zone (Z1–Z5) for a workout or an extra leg, there was no way back to "no specific zone" — the dropdown only ever listed the five zones. Both zone pickers (the main workout form and each extra leg) now have an explicit "No specific zone" option (`src/lib/utils/zone-select.ts`).
- **A more colorful, better-organized workout form.** The core fields (date, discipline, duration/distance, zone, title, notes) are now grouped in one bordered section instead of a long flat list. The discipline picker shows each sport's own colored icon (the same colors the calendar card uses) in both the dropdown and the collapsed trigger; the zone picker shows a small color dot per zone; the dialog's title shows the selected discipline's icon; each extra sport leg is tinted in its own discipline's color, the same color it shows on the calendar (`DisciplineIcon.tsx`).
- **The coach can suggest multi-sport ("brick") workouts.** "Plan my week" can now propose a session with extra legs (e.g. bike then run), saved exactly like a hand-made brick workout — same schema, same database row, same "+1 per discipline" dashboard counting. Confirmed working end-to-end: asked for a specific brick via the "ask for changes" box, the coach proposed one with a real extra leg, and it rendered correctly in the preview and would save correctly. Honest caveat: on a bare "Plan my week" with no specific ask, the coach usually still proposes a bike-then-run brick as two separate same-day workouts rather than one two-leg entry — getting it to reliably pick the newer, less common field unprompted is a prompt-tuning problem, not a code gap, with diminishing returns to chase further; asking for one specifically (as tested) works.
- Checked with 11 new automated tests (343 total) and the real-app testing described above.

## Restoring navigation feedback, safely this time (2026-10-02, later)

Removing `loading.tsx` (the entry above) also removed the only thing giving instant feedback *during* a navigation — `PageTransition`'s fade only affects content once it has already arrived, so clicking a nav link went back to feeling like nothing happened for a moment. That's what "the loading animation doesn't work" meant.

- **A small pending dot on each nav link.** Calendar, Dashboard, Coach, Friends (top bar and the mobile bottom bar) now show a small fading/pulsing dot next to the link while its page is still loading, using Next's `useLinkStatus` hook (`NavLinkPending.tsx`) — a per-link, client-only signal built for exactly this, with no Suspense boundary and no route-level fallback, so it cannot reproduce the hang. It only shows up when a navigation genuinely takes a moment (an already-prefetched page skips it entirely, which is correct — most clicks will stay silent because they're instant).
- Confirmed the page content itself was never actually invisible or broken — a `getComputedStyle` check during this investigation misleadingly reported `opacity: 0` on the animated wrapper and on an open dialog, which a direct screenshot proved wrong (both were fully visible); that reading is unreliable for actively-animated/composited properties in this automation setup and shouldn't be trusted for this kind of check again. The real, confirmed gap was the missing pending feedback, now fixed.
- Checked with 3 new automated tests (346 total) and a walkthrough of the real app (every nav link, no console errors, no crashes).
- **Follow-up the same day: the dot wasn't enough** — feedback was "I like the previous loading animation, now it feels like the screen freeze then move to new tab." Brought the big branded overlay back (spinning zone-dial logo + "Loading…" over the page content), but through client state this time, never `loading.tsx`/Suspense: `NavigationProgress.tsx` holds an `active` flag in React context, every nav link's `onClick` calls `start()` to flip it on immediately, and it's cleared the instant `usePathname()` reports the new route. A hard-coded 4-second failsafe timeout clears it regardless, so a cancelled or same-page click can never leave it stuck — the one failure mode this whole rebuild exists to rule out. Confirmed in the real browser with a MutationObserver (screenshot timing is too coarse to catch a transient overlay): it mounts the instant a nav link is clicked and unmounts the instant the route changes.
- Along the way, found and fixed an unrelated pre-existing hydration mismatch firing on every single page load: `ZoneLogo`'s needle coordinates were passed as raw `Math.cos`/`Math.sin` floats, which can differ in their last few bits between server (Node) and client (browser) builds of V8. The zone-arc paths already guarded against exactly this with `.toFixed(2)`; the needle didn't. Same fix applied.
- Checked with 5 new automated tests covering the overlay's full lifecycle (show on start, clear on route change, clear via the 4s failsafe even without a route change, hidden by default, hook throws outside its provider) — 356 total, full `npm run check` clean.
